## 音乐下载 media_download

> 来源:分家前 AGENT.md「7.1 影音(PLAN §9)」L271。

- **音乐下载 `media_download`(2026-07-27 落地;用户拍板三件:默认存系统「下载」文件夹 / 格式跟着源走、不做 mp3 转码档 / 批量做但发现是合集先问用户单个还是全部)**:第四媒体原语,把网络页面的音轨存成本地文件(需知里有音乐目录时模型传 `dir`)。**解析与播放同一条链**(yt-dlp / cookies / AuthRequired 分类全复用),只换**下载专用格式串** `resolver::DOWNLOAD_AUDIO_FORMAT = "ba/b"`——质量优先:源里有无损(B 站大会员 Hi-Res FLAC)就拿、存 `.flac`,否则最高码率 AAC 存 `.m4a`(播放用的 AUDIO_FORMAT 秒开省流,**刻意不动**;两个诉求分家)。落盘 = web_download 同款(net::Client 流式 + `.part` 临时件 + `dedupe_path` 永不覆盖),**防盗链 Referer/UA 头原样带上**(yt-dlp 给的,relay 同款);单文件闸 500MB(单源 `download::AUDIO_MAX_BYTES`,web_download 的 50MB 是任意网页文件口径、不适用点名曲目)。末步 ffmpeg `-c copy` 整理标准容器(fMP4/.m4s → .m4a 带 faststart、FLAC → .flac)+ 写标签——**全程不转码**(有损转有损 = 倒退,mp3 档明确不做;标签写什么见下条二批修正:UP 主绝不进 artist);ffmpeg 缺席/失败**不阻断** = 原样保存 + 结果如实说(§3.5)。**需要登录 ≠ 失败**(播放同口径,弹扫码)但**无自动重下**(区别于播放的 pending_play):话术引导登录后再调一次。**批量 = 用户确认后才 `all=true`**(工具描述引导「合集/分P 没说清先问」;eval 守卫 `download-batch-confirm` / `download-batch-explicit`):episodes 发现与播放同链、不成系列退化单曲,成系列**分离 job 后台逐首下**(tasks 进度 `step.audio_batch` i/n;有没下成的按 fail 收尾点名数目 `task.err.audio_batch`;登录半路失效 = 弹扫码 + 剩余搁置不空转),封顶 `BATCH_MAX=100` 超了如实退回分段。**范围参数 `from`/`to`(2026-07-27·六批,真机 110 首合集实锤)**:原「超了让用户分批」的话术**没有对应参数兑现** = 空头承诺,模型只能绕去 web_render 扒分P链接(承诺与机器脱节,能力对账同款教训)→ `all=true` 配 `from`/`to`(第几首到第几首,1 起含两端,None 边回落头/尾;`resolve_range` 越界如实报「一共 X 首」= 跳集同口径);大合集分几批下、「只要合集第 N 首」= from=N to=N;超容量的退回话术带**现算的分段建议**(先 from=A to=B,再 from=C to=D);登记处标题/收尾汇报/工具话术都带段(「合集第 1-100 首(共 110 首)」)。白捡的闭环:下载落同一文件夹 → 整夹连播/循环随机直接吃到;下过的歌下次点播 fs_find 本地命中 = 秒开、离线、不再联网解析。顺手:`files::human_size` 上移成单源(tools::fs 留 `pub(super) use` 转发,老调用点零改)。版权口径:只下用户自己账号能播的内容存本地自用(同一套 cookie,付费内容照旧 AuthRequired 拦),不碰加密流破解、不接野 API 源。**Mac 全绿(508+16)/ 触点零警 / i18n 镜像 671;真 B 站单曲、大会员 Hi-Res 真出 FLAC、合集批量、Windows 真机(防盗链下载/中文文件名/faststart 文件真机播放器认标签)= 真机 watch(PLAN §9)。**

## BT / 磁力下载 torrent_download

> 来源:分家前 AGENT.md「7.1 影音(PLAN §9)」L282–L292。

- **BT/磁力下载 `torrent_download`(2026-07-29 落地;用户四轮追问后拍板做种策略「A」)**:第六媒体原语,把**用户给出的**磁力链 / 本机 `.torrent` 下成本地文件。**下完落进文件夹 → `media_play` 那条本地播放链(按需 HLS 转码 / 音轨切换 / 整夹连播 / 续播记忆 / `fs_find` 本地优先命中)全部白拿,relay 与前端零改** —— 因为 `play()` 本就按 `is_local_path`/`is_dir_path` 分派,这是一期能这么小的根本原因。
  - **版权口径的兑现方式(重要,别误读成翻案)**:§7.1 那条「不接野 API 源」**没有放宽**。翻的是「有没有 BT 下载能力」,不是「要不要内置片源」——真正能兑现的边界 = **不写死任何站的选择器、不内置片源搜索、不维护片源目录**;链接由用户给,定位与 `web_download` 完全一致(用户给什么下什么,我们是下载器不是内容源)。⚠️ **如实记档:「不去站扒链接」不是可执行的闸** —— `web_render` + LLM 今天就能打开任意页面把 magnet 读出来,工具描述里那句只是引导、拦不住被用户说服的模型;真实变化是**组合的自动化程度**(「找部XX下来看」变成一句话),这一点用户已知情并接受。
  - **做种策略 = A(§4.11 用户拍板)**:下载期正常上传,**下完立即 `Session::pause` 停止做种**。不是随手可调的旋钮——BT 的 choke/unchoke 是 tit-for-tat 互惠(peer 只把带宽给「也在给自己传」的那几个),**下载期不传 = 显著变慢甚至下不动**;librqbit 的 `disable-upload` feature 与 per-torrent `ratelimits.upload_bps` 都在,要改回来容易、但要连带接受速度代价。**已向用户讲清:下载期就在分发,这部分关不掉**(上一轮我把「下完停」说成能消除分发,是错的,已更正)。
  - **能力天花板 = 种子真实健康度,与迅雷不可比(期望管理,别再重复评估)**:迅雷会员快是因为它是 **P2SP** —— 有服务器缓存池 + 跨协议聚合 + 离线下载,热门资源你以为在下 BT、其实大半字节来自它服务器(所以也不受 tit-for-tat 惩罚,也因此被 PT 站普遍封杀);会员卖的是**服务器带宽优先级**,同网盘限速一个道理。我们没有服务器集群 → **热门种子能跑满带宽(与迅雷相当),冷门/0 seeder 救不了**。这正是一期只做「下完再播」的理由:速度不可预测,边下边播赌不起。
  - **机制**:`librqbit 8.1`(`default-features=false` + **`rust-tls`** 与全局 reqwest 的 rustls 对齐,关掉 axum HTTP API/webui/sqlx;净增 50 个 crate —— 树里 218 个、168 个我们已有)。引擎 `media/torrent.rs::TorrentEngine` **懒建**(`Inner.torrent: OnceCell`,同 relay):不用 BT 的用户零成本,更关键是**不平白发 DHT 包**(那是会被运营商画像的流量特征);`persistence: None` = 重启不自动续种(§6.4 派生可丢 + 免「关了 app 还在偷偷做种」)。流程 = add → `wait_until_initialized`(取 metadata)→ **体积闸** → 2s 轮询(beat/step/查取消/查停滞)→ finished → **pause 停做种** → 报文件清单。**恒走后台 job**(BT 动辄几十分钟,绝不占回合):`bgtasks` 登记处白拿〔此刻〕一行 / `task_status` / `task_cancel` / **收尾自动唤回合汇报** / 10min 卡死看门狗;`bg` 新增 `running_count_of(prefix)` 给 BT 自己的并发闸。
  - **§4.11 拍板的常量(全在 `media/torrent.rs` 顶部单源)**:单种子 `TORRENT_MAX_BYTES=50GB`(`media_download` 的 500MB 是「一首歌」口径,影视量级另开一个数)· 并发 `MAX_CONCURRENT=3`(再多只是分摊带宽,满了如实退回不排队)· `METADATA_TIMEOUT=60s` · `NO_PROGRESS_TIMEOUT=5min` · 缺省 `DEFAULT_ONLY_RE`= 视频扩展名白名单(影视种子常年混样片/nfo/「最新地址.txt」广告;全下传 `only="."`)· 落盘缺省 = 系统「下载」夹(同 `media_download`)。
  - **`.torrent` 比磁力链可靠得多,工具描述明写**:磁力链要先从 **DHT 取 metadata,而 DHT 走 UDP** —— 国内运营商的 P2P 限速正是冲 UDP 来的(移动 2025-05 起全国部署),这是最容易卡死的一步;`.torrent` metadata 内嵌、跳过这步。失败话术逐类给因(拿不到种子信息 / 太大 / 一直没数据进来〔没人做种·防火墙没放行·运营商掐了〕),**绝不含糊报「失败」**(§3.5)。
  - **永不覆盖 + 不替用户删**:`overwrite:false`(§7.2 可逆三规①,撞同名如实退回不静默改写);放弃种子只 pause+delete 出 session、**不删已下的字节**(半成品留着能续,要清理走 `fs_trash`)。
  - **边下边播 = 二期,刻意不做**:需要 `Entry::Torrent`(rqbit stream 端点是 HTTP+Range,与 relay 同构、改动很小)+ 预缓冲起播闸(复用 0.2.6「两轨都有货才 play()」)+ 欠速检测。押后理由 = 「下完再播」拿到的是**和本地片一模一样**的体验(seek 瞬时、不卡),边下边播只换来「立刻能看」却赔上 seek 断崖;等真实网速手感摸到再定。
  - **Mac 全绿(545+16,新增 7 测)/ clippy 触点零警 / 完整工作区构建通过 / vue-tsc / i18n 镜像 747=747(新增 7 键);真机 watch(PLAN §9)**:真磁力链能不能拿到 metadata(国内 DHT 是最大变数)· Windows 防火墙首次弹框不放行时是不是走到「一直没数据」如实退回 · 真速度与码率的关系 · 下完确实停止上传(任务管理器看上行) · 大种子 50GB 闸 · 中文种子名落盘。

## ffmpeg 直通 ffmpeg_run(裸参数 + 边界闸 + 探测形)

> 来源:分家前 AGENT.md「7.1 影音(PLAN §9)」L293–L300。

- **ffmpeg 直通 `ffmpeg_run`(2026-08-03 落地;用户拍板「一个 String 传参最灵活、开发最简单」→ 方向采纳、三处收口,灵活性不打折)**:第七媒体原语,把 ffmpeg 整个开给模型(剪一段/转格式/抽音轨/拼接/调音量/变速/压缩/截帧/烧字幕 = 模型自己的 ffmpeg 知识组参数),**程序不做操作矩阵**(§5;结构化参数集只会做减法 = 「话术承诺了、参数没给」的合集 from/to 老坑)。**§6.3「参数无后门」的有闸例外**——那条管「万能口袋绕过类型」,这里 args 就是工具本体,闸全在边界:
  - **args = 字符串数组,不是单 String**:JSON 数组零转义直喂 `Command::args`,免 shell 分词/引号/中文文件名转义地狱(数字项宽容转字符串,arg_bool 同族 §4.4);
  - **输出永不进 args**:`output`(文件名,扩展名定格式)+ `dir`(缺省 = 第一个输入旁)独立参数,程序落盘 —— 授权圈 create + dedupe 永不覆盖 + 临时件写完改名(§7.2 三规①),输入原件一字节不碰。这是关键收口:从裸参数里认输出得认全 ffmpeg 几百个 flag 谁吃值,认错一个 = 授权圈旁路;提成参数后问题整个消失;
  - **边界闸单源 `tools/ffmpeg_run.rs::scan_args`**(纯函数,单测钉着):`-i` 后 token = 输入,逐个过授权圈 read(绝对路径 + 必须存在的本机文件);**滤镜内嵌路径**(subtitles=/ass=/movie=/amovie=,认引号/`\:` 转义/`filename=` 形,词边界防 `bypass=` 误配)抽出来同过 read 闸,Windows 盘符冒号未转义给明白话;拒收:`://`(ffmpeg 自带网络栈,绕 net::Client)/`pipe:`/`-y`/`-n`/`-f concat`(列表文件 = 圈外读旁路,拼接走多 `-i` + filter_complex concat)/`-f lavfi`/一小撮旁路写文件 flag(-passlogfile/-report/-dump_attachment/-segment_list/-filter_script 族,带 `:spec` 后缀按前缀拦)/**孤零零的裸值**(每个裸值必须紧跟它的 flag —— 孤值 = 想把输出塞进 args 的未过闸写出口);
  - **执行 = 先跑再说,不做成本预测**(裸参数估不准耗时,预测矩阵是死路):`media/edit.rs` 回合内等 `IN_TURN_WAIT=30s`(§4.11 单源)跑完当场回;没跑完自动转 bgtasks 后台(〔此刻〕/进度/取消/收尾唤回合汇报/10min 看门狗全白拿;`-progress pipe:1` 解析出「处理到第几秒」,**只在真推进时 beat** —— 僵住的 ffmpeg 不喂看门狗、10min 判卡照常;cap 满 = kill + 如实退回);`TempGuard` 兜一切半路死(回合取消/看门狗 abort → kill_on_drop 杀进程 + 临时件即删);失败带 stderr 尾巴(2000 字符闸)回喂模型自纠,工具描述引导「长片先剪十几秒试参数」;
  - **`-c:v h264` 占位 = 确定性替换**成这台机器探测出的最快编码器(relay 的 `video_encode_args` 提成单源,GPU 探测缓存与播放转码链共享一次;显式写 libx264/h264_nvenc 一字不动),结果文本如实说用了哪个 —— 是文档化替换,不是静默改写;
  - **探测形(同日追加;用户点破「为啥不把 ffmpeg 输出直接还给模型」)**:`output` 可选 —— **不给 = 只探不产**,照终端习惯 `ffmpeg -i 文件` 跑一遍、**原样返回 stderr 信息横幅**(时长/编码/音轨/标签;截断保**头部** 4000 字 `PROBE_OUT_MAX` 单源;不看退出码 = probe_with_ffmpeg 同款;输入照过 read 闸,无输出落盘动作天然只读、秒回不进后台)。「去掉结尾 N 秒」由此闭环:先探时长 → 模型自己算绝对时间点(算术归模型,嘴控音量相对量同款哲学);此前议过的 media_probe 独立工具被这个形**取代**(「读塞进写工具」的顾虑不成立 —— 工具本体就是「跑 ffmpeg」,查信息是它的原生用法);「-to 负数=距结尾」魔法参数维持不做。加工路的 stderr 仍压 -loglevel error 不变(报错尾巴要干净)。**长输出落临时文件的机制项目里没有、也不需要**:量约束三形态 = 汇总+点名(fs 写类/批量汇报)/截断+offset 续读(web_fetch·web_render read·fs 读类三原语,2026-08-15 起 fs_list/fs_find 也在内)/截断+如实说明(本条两处)。**2026-08-15 用户提过「超长一律落临时文件让 agent 去翻」的通用包装层,评估后不做**:「太长」只是表象,底下三种病因不同 —— 全量已在手里装不下(能包)/ 压根没产出(fs_find 走到一半就停)/ 是聚合(fs_usage TOP-N),通用层只救得了第一种;而第一种恰恰是**重跑很便宜且必须新鲜**的活,给工具加 offset 比落文件更省(零生命周期:不用 TTL、不用清扫、不会读到过期快照撒谎)。临时文件真正合适的是「产出贵/不可重现」的长结果,那属于**产物**该落到用户看得见的地方,不是 tmp;

## 听音频原语 read_audio + 配歌词梯子顺序

> 来源:分家前 AGENT.md「7.1 影音(PLAN §9)」L303。

- **★听音频原语 `read_audio`(2026-08-15;用户「儿歌匹配不到歌词,有没有更 AI 的方式」→ 拍板「模型的词 + 音频的轴」)**:`read_image` 的耳朵版 —— 本机音频 → 「第几秒唱/说了什么」(`[mm:ss.xx] 文本` 逐句)。**轴来自音频本身、不是编的**,与「绝不编造时间轴」纪律不冲突(禁的是凭空编)。配歌词的正解 = **模型的词 + 音频的轴**:ASR 不认字、模型不知道时间,弱点正好互补 → 原语只出「第几秒听成什么」,**对齐交给模型**(此前设想的编辑距离/DTW 对齐代码因此**不做** —— 模型比它强,§5)。机器 = 现成件三段:ffmpeg 解码(新 `decode_file_pcm16k`:直接 `-i 路径` + `-ss`/`-t`/`-vn`,不经内存和临时件 —— bytes 版那条是给手机语音消息的)→ silero VAD 切句(段起点 = 时间戳)→ 逐段 ASR(与唤醒/听写共用缓存的识别器)。**零新组件、零新模型**;接线 = `ToolCtx.voice: Option<VoiceRuntime>` + `Engine::set_voice`(`set_web_renderer` 同款接缝,壳层 boot 注入;engine → voice 与 engine → media 同向,voice 不反依赖 §6.1)。常量单源 `voice/mod.rs`:`SING_HANGOVER_S=0.35`(唱歌句间停顿比说话短,沿用说话档 800ms 会把整段连成一坨)· `SEG_PREROLL_S=0.2`(**mac 实测逼出来的**:VAD 起点卡在能量抬起那一刻、声母在它之前,不带 pre-roll「跑得快」听成「得快」;唤醒/听写链早有同款,这条路补上)· 工具侧 `MAX_SECS=600` / `PAGE_LINES=200`(fs 读类同款「一页 + 报总数 + offset」,长音频靠 `from` 分段听)。**回合内等不转后台**(读类结果得当场回模型手里才接得上下一步),超时 300s。配套出厂技能「给歌配歌词」(12→13 条)。**梯子顺序 2026-08-16 用户纠正过一次,别再排反**:lyrics_fetch 查库 → **web_search/web_fetch 上网找** → 自己确实会唱的才默写 → read_audio 听着补轴。理由两条:① 歌词站常直接给**带 [mm:ss] 的 LRC 原文**,搜到就词轴双全、根本不用听,比听出来的准得多(原稿把搜索排在第 4 条当「拿不准时的补充」= 把最好的一档埋了);② **版权上搜索也更稳** —— 模型凭记忆默写整首流行歌词 = 从权重里复制受版权保护的作品(技能明令禁止),从公开网页取回存本地自用与「只下自己账号能播的内容」同族,所以搜索该在默写**之前**。**听退成「拿轴」的手段,不是「拿词」的手段**(词以库/网上/确实会唱的为准,听出来的字本来就会错)。红线随之改准:**时间戳只有三个正当来源 —— 歌词库、搜到的 LRC 原文、read_audio;一个都不许自己编**(原表述「只能来自 read_audio」已不准确)。其余纪律不变:受版权保护的流行歌查不到就如实说、对不上号的句子宁可跳过不硬凑(少一行 < 错位)、同名 .lrc 已存在就跳过不覆盖。**mac 合成语音端到端验过**(`#[ignore] real_audio_transcribe_probe`,`LW_AUDIO_PROBE` + `LW_VOICE_DIR` 免重下模型):轴准递增、≈9 倍实时(4 分钟的歌约 27s)、重复句 4/4 不丢、pre-roll 后首字不再削;**但混合内容那条 6 句里丢了 1 句、未完全定位** —— 真儿歌/真流行歌的错字率与漏句率 = 真机判据(决定这条路值不值得往下投)。
