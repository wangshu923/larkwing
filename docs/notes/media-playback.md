## 播放分两条路:自适应流走 MSE(shaka)、单流走原生;B 站 DASH + 本地 fMP4-HLS

> 来源:分家前 AGENT.md「7.1 影音(PLAN §9)」L259。

- **播放分两条路:自适应流走 MSE(shaka)、单流走原生(2026-06-20 起,Stage 1 落地)**。背景:原来把 B 站 DASH 两条流用 ffmpeg `-c copy` 混成**一条渐进 fMP4** + `?t=` **重启式 seek**,拖进度条后**音画错位几秒**(拷贝视频回退关键帧、另一轨不回退,muxer 又归零 → 音频领先)——这是重启式 seek 的**固有缺陷**(B 站 + 本地转码都中),`make_zero/aresample/noaccurate_seek/copyts` 全验过修不了。**B 站本来就是做好的自适应流**(像网页那样),所以治法 = 别再混流:relay 合成一份 **DASH MPD**(`Entry::Dash`,段经 `/s/` 同款防盗链头+Range 透传,sidx 字节范围由 `probe::probe_sidx` 探 .m4s 头得到、`build_mpd` 合成),前端 **shaka(MSE,懒加载)**经 `NowPlaying.manifest_url` 播 → 播放器自己管时间轴 → **原生 seek + 天生同步**,且 **B 站链路彻底脱 ffmpeg**。判据:`manifest_url` 有值 → shaka;否则 `stream_url` 挂原生 `<video>/<audio>`(直传文件/单流,原生 seek 本就对)。DASH 探不到 sidx / 无时长 → 回落老的 ffmpeg 混流(能放、seek 仍错)。**CORS**:shaka 用 `fetch` 拉段是跨源(app 源 ≠ relay 回环口),`/dash/` 端点必须带 `Access-Control-Allow-Origin` + 暴露 Range 头(`<video src>` 不查 CORS、fetch 查)。**B 站这条 2026-06-20 Windows 真机验通**(拖进度条音画同步 ✓,shaka/MSE 在 WebView2 立住)。**本地不兼容文件(HEVC/AC3/mkv)= Stage 2 也落地了(2026-06-20)**:不再走 /m/ 渐进混流,改 **HLS 按需切片(fMP4 段)**——`Entry::FileHls`,`/hls/{token}/index.m3u8` 由 probe 的 duration 合成**完整 VOD 列表**(全段列出 + 共享 `EXT-X-MAP:init.mp4` → shaka 知道完整时长、可任意 seek)+ `/hls/{token}/s{N}.m4s` 按需 `ffmpeg -ss N*6 -t 6` 出一段**单 moof 分片 mp4**(`empty_moov+default_base_moof` + 大 `frag_duration` 逼单 moof)。**段走 fMP4 而非 mpegts(2026-06-20 二修,头号坑)**:最初发 mpegts(.ts)段,shaka 用 **mux.js 把 mpegts transmux 成 fMP4** 喂 MSE —— 实锤**视频轨 transmux 在 WebView2 失败**(append code **3015/3016**)→ **黑屏**(音频没事就视频炸,正是 transmux 那步;`-output_ts_offset` 让 .ts 跨段 PTS 连续也救不了,病不在 PTS 在 transmux)。改 fMP4 段 = B 站 DASH 已验通的同路、MSE 直吃、**绕开 mux.js**。**关键:ffmpeg 输入 seek 出的分片 `tfdt.baseMediaDecodeTime` 恒被重置为 0**,不修则各段全堆在 0 秒 → 还是错乱 → `probe::patch_segment_tfdt` 从 init 读每轨 timescale、把段内 tfdt 改回**累计起点**(`start×timescale`)+ `moof_segment_end` 剔除 `-f mp4` 尾部写的 `mfra` → 产出**标准累计-tfdt fMP4-HLS**,shaka 按 tfdt 直接拼接、不靠播放器额外算 offset。**段一律转码视频 + 下混立体声 AAC(2026-06-20 三修,Mac Chromium MSE 复现实证,`build_frag_cmd`)**:① **视频必转码**——`-ss`+`-c:v copy` 只能落关键帧、切不准 → 段时长漂(请求 6s 出 8s)、段间重叠/错位;转码则每段从干净 IDR 起、恰好 6s、avcC 跨段一致 → MSE 拼得上;② **音频必转码**——视频转码 + 音频 `copy` 时 fragmented muxer 把样本时长写成 **2×**(段被拉长一倍),两轨都转码即消;③ **下混立体声 `-ac 2`**——多声道 AAC 声道布局不明确(AC3/DTS 转 AAC 常见)→ **MSE 拒 append 整个 init**(报在 video 轨 = 用户「video:2 code=3014 黑屏」的真因),立体声永远能 append。代价 = 已是 H.264 的片子(仅因容器/音轨进 HLS)也重编视频、弱机吃 CPU,但它们当前本就黑屏(mpegts 链路)不是回退;后续可给「视频已兼容」者走整文件 copy-remux→DASH 省 CPU。无临时目录 / 无会话(每段现切现回、用完即弃);seek = shaka 请求目标段 → 现切现回 → 原生 seek + 同步。前端 `manifest_url` 路径对 DASH/HLS 通吃(shaka 自动认),**前端零改**。无时长 → 回落 /m/。**✅ 2026-06-30 Windows 真机验过**:B 站已验通;本地 fMP4-HLS 的 shaka 拼播 + 拖动同步 + HEVC 重编码 CPU 可接受均已验。**Mac 已把能验的全验了**:用**预览浏览器(Chromium,与 WebView2 同 MSE 内核)裸 MSE 复现** —— 复现了 5.1-AAC init append 失败(3014)+ 证实 fMP4 段/tfdt 累计/立体声修法后 init+s0+s1 全 append 成功、时间轴连续;真·ffmpeg 端到端切段→patch_tfdt→可拼;单测全绿(见 §8.1)。

## 多集自动续播:队列机器 / 剧集发现 / 续播规则 / 续播记忆

> 来源:分家前 AGENT.md「7.1 影音(PLAN §9)」L264。

- **多集自动续播(2026-06-20 落地;B 站合集/分P + 本地剧集 + 集级续播记忆)**:动画片/电视剧放一集自动接着下一集。机器**来源无关**——`MediaRuntime` 持一份队列(`Playlist{series_key, entries:Vec<EpisodeRef{id,url,title}>, index, audio_only}`,app 级瞬态、派生可丢),`advance(±1)` 只挪 index、`play_entry` 现取现播(流地址永不过期);只有「发现剧集清单」分两路:**B 站**走新 `MediaSource::episodes`(view API `x/web-interface/view`,**合集 ugc_season 优先、其次分P pages**;分P 的 P1 用裸 bvid url 对齐 url 匹配),**本地**走 `local_episodes`(同文件夹 + 同类扩展名桶 + **数字骨架分组**防平铺电影库误触 + 自然排序;§确定式扫描,用户否决了 LLM 排序——规模/可复现/续播稳定性)。`NowPlaying.playlist:{index,total,resumed}` 驱动前端「第N/共M集」+ 上/下一集按钮;前端 `ended` → 非末集调 `media_advance(+1)`(不绕 LLM)、保持全屏不退出;嘴控 `media_control` 加 `next/prev`→`advance`,**再加 `episode`(第 N 集绝对定位,2026-07-03 v0.2.4 用户点破「队列本就有 m/n」)→ `jump_to_episode`,与 advance 共用 `switch_episode`(越界报「一共 X 集」、跳当前集=从头重放、切集照落续播进度);队列是 core 单一真相,模型只说集数不碰链接(B 站合集每集独立 bvid 也照跳),「跳到最后一集」= 从〔此刻〕的「共M集」自算**。**续播规则(2026-09-07 重做,取代原「自然起点 / 点名某集」判法)**:路径 / 链接**只用来认剧、不再从「传的是第几集」推断意图**——模型习惯拿上次用过的某一集路径当整部剧的把手,老规则把它当「点名要看那集」、进度都不查(真机「昨晚看到 4 集今天回到 2 集」的候选病灶;另一候选 = 工具路径按说话人、自动续播按主人各记一行);现在:`episode=Some(N)`(`media_play` 新参数,用户点名「看第五集」)→ 第 N 集从头;`restart` → 第一集从头;否则有进度就接上(停在第 i 集 → 第 i 集 + **集内秒数**;第 i 集看完 → 第 i+1 集从头;末集看完 = 整部从头);没进度才用传的那个文件当起点。决策落一行 info 日志「续播决策」(排续播问题看它)。**续播记忆 = 专用域 `store/media_progress`**(不进记忆系统——高频结构化运行态非「关于人的事实」),**按家记不按人(迁移 0032,PK 只剩 series_key,多人多行保留最新;用户拍板「暂时不接到人,声纹识别太低」;`last_user_id` 只记上次谁看的,删家人不动它)**、**只存集身份 + 相对名,series_key 本地用 `local:FNV(目录+骨架)` 单向哈希,绝不落绝对路径**(§6.2);**集内秒数**由前端心跳落盘(前端本就 15s 回报一次,core 每 30s 真写一次 `set_position`,暂停 / 停止 / 切集立刻;按标题核对防切集瞬间迟到的旧心跳写进新一集;短于 10 分钟的内容不记),读侧三闸单源 `media/mod.rs`(看了不到 30s 当没看、离结尾不到 90s 当看完;§4.11 过程默认待确认);**单部电影按文件身份续**(`local:file:FNV(小写全路径)` / `web:FNV(页面地址)`,放歌不记);工具回话「接着上次,从第 4 集 12:30 继续」;起播 / 切集经 `track_progress` 落行,失败不挡播放。剧集发现改返回 `Series{key,title,entries}`(剧名 = 文件夹名 / B 站 season_title / ugc_season title / 分P 视频标题),关怀条「继续看《X》」显剧名不显集名。**✅ 2026-06-30 Windows 真机/真网验过**(同 §8.1):真 B 站合集/分P 的 view 解析 + 自动切集播放 + 跨会话续播 + 本地文件夹扫描/续播链。

## relay 注册表从「只增不减」改成按字节权重有界(2026-09-08)

> 来源:2026-09-08 优化批(全仓体检 → 一起修)。规则句在 AGENT §7.1,常量进 §4.11 待拍板。

- **病**:`media/relay.rs` 的 `streams: Mutex<HashMap<String, Arc<Entry>>>` **从不清理** —— 老注释自己承认这件事(「`streams` 注册表本身从不清理(每次播放留一个 entry)」,写在 `THUMB_CACHE_MAX` 那条解释「为什么缩略图缓存要全局有界」时)。每次点播注册 1–3 个 token(播放臂 + `Thumb`/`Sprites` + `Cover`),切集 / 切音轨 / 兜底重放各再留一份;连播一季或歌单循环几天就是几十上百个常驻。轻的 entry 只是几个 `PathBuf` 无所谓,**真占地方的是 `Entry::FileAdaptive.video_init`**(注册时预生成并缓存的整份 ftyp+moov,4K 长片能到几 MB)、`Dash.mpd`、`Sprites` 的帧索引。
- **为什么不能按条数一刀切**(这是设计上唯一的坎):`MediaRuntime::attachment_url` → `file_url` → `relay.register_file(path)` —— **聊天历史里每张图也在同一张表里注册一个 `Entry::File`**(一条约 100 字节)。重开一个 200 张图的会话就是 200 个 token,且每次 `resolveThumbs` 都会为同一张图注册新 token(旧的从前就那么泄漏着)。按条数限量 → 老图的 localhost URL 被挤成 404 → 图卡破图。
- **修**:`StreamRegistry`(map + 插入序 `VecDeque` + 权重和)按 **字节权重** FIFO 淘汰,权重由 `Entry::weight()` 粗估(`BASE 256` + `video_init.len()` / `mpd.len()` / sheet 索引;其余臂只有几个路径,记 BASE)。三道界:`STREAMS_MAX_BYTES` 64MB(重型 entry 的常驻上限)· `STREAMS_MAX_ENTRIES` 500(条数 backstop,几乎只由图片附件触达,一屏聊天最多 200 张 → 留足余量)· `STREAMS_MIN_KEEP` 8(**保底优先于前两道** —— 全是巨型 entry 时宁可字节略超,也不许淘汰最近几条:**正在播的那条就在里面**)。淘汰是 FIFO 而非 LRU,因为播放是顺序往前走的、老 entry 播完就没人请求。
- **测试踩的一处**(值得记):第一版单测断言「压回后 `bytes <= STREAMS_MAX_BYTES`」直接红 —— 40 个 8MB entry 被压到 8 条 = 64.01MB,略超。这不是 bug 而是 MIN_KEEP 保底的**有意**结果,断言该写成「压到保底条数」;顺手把这个优先级写进常量注释,免得后人来"修"。守卫 `relay::tests::stream_registry_evicts_by_bytes_and_keeps_recent` 三段:500 条轻 entry 一个都不许掉(老图回归)· 40 个重 entry 压到保底且最新那条必在 · 单条就超上限时也不许把自己淘汰掉。

## 片尾预告改「提前 5 秒」+ 进度条标片头片尾 + 倍速切集丢失(2026-09-10)

> 来源:2026-09-10 用户看片时提的三条(「进度条上把片头片尾的位置标一下」/「片尾跳过延迟五秒不太对」/「自动换集之后倍速仍显示 1.75 实际像 1.0」)。规则句在 AGENT §7.1(片头片尾条 + 工具七原语条),常量在 §4.11。

- **① 片尾:从「越线后数 3 秒」改成「提前 5 秒预告、到点直接切」(用户拍板)**。原设计(2026-09-07 五批)是自然越过 `outro_start` 才开一个 3 秒 `setInterval` 倒计时,数完切集 —— 用户实际看片的体感是「片尾都开始放了还得干等」,**倒计时的位置放错了**:它该是「切之前的招呼」,不是「切之后的延迟」。改成 `OUTRO_NOTICE_S = 5`:自然播到 `outro_start − 5` 起出预告「即将播放下一集 · N 秒」(带「取消」),越线那一刻直接 `autoNext()`。
  - **实现上把 interval 整个删掉了**,预告改成**从播放位派生的 computed**(`outroNotice` = `outro_start − position` 落在 (0, 5] 才有值)。好处不是省一个定时器,是**生命周期自己就对**:暂停 / 拖走 / 换集 / 取消都自然消失,不用再在四五个出口 `clearInterval`(原先 `cancelCountdown` 挂在换集 watch、取消按钮、`onUnmounted` 三处)。倒计时读数由 `Math.ceil` 从播放位现算,timeupdate ~4Hz 足够。
  - 「拖进片尾区 = 想看,不切」的语义**扩到整个预告窗**:`jumped && p >= outro_start − 5` 就把这一集的 `outroDone` latch 掉(不预告也不切)。自然播到头仍走 `ended → autoNext`,不受影响。
  - 预览页逐帧验过(0.5s 一步喂 `state.position`):284.5 无预告 → 285 出「5 秒」→ 逐档数到 289.5 的「1 秒」→ **290 那一拍 latch + 切集、预告同拍消失**;拖进窗口与点「取消」两条抑制路各验一遍。
- **② 进度条标出片头起 / 片头止 / 片尾起**(用户:「小竖线或者大的圆点都可以,你看哪个好看就行」)。选了竖线:`.skip-mark` 2×10px 骑在 3px 轨道上,精确、不把控制条撑高。三处细节值得记:
  - **颜色用 `--attn`(琥珀)不是 `--accent`** —— 轨道已播区就是 `--accent` 填充的,同色标上去等于隐形;外描一圈 `rgba(0,0,0,.45)` 让它压在亮画面上也读得出。
  - **`z-index: 1` 是必须的**:标记与滑杆同在 `.scrub-track` 里,滑杆在 DOM 里排后面,不提层就被它自绘的轨道底色盖住。代价是与拇指重叠时 2px 线画在 11px 拇指上 —— 可接受(标记本就该恒可见)。
  - **`pointer-events: none`**:轨道上还压着 hover 读数 + 缩略图气泡与右键标记菜单,标记吃了指针事件就会在那三个点上出现「hover 突然失灵」的怪病(同族教训见 §6.7 clip-path 裁掉外沿浮层那条)。
  - 时长未知(`/m/` 渐进混流 `el.duration = Infinity`)一个都不画 —— 宁可不标,不标错地方。
- **③ 倍速切集丢失:真凶 = 只设了 `playbackRate` 没设 `defaultPlaybackRate`**。现象是「切下一集后倍速仍显示 1.75、听着像 1.0x」,而 core 的镜像是对的 —— 所以病在**元素**这一侧。
  - **机制**:HTML 媒体元素的「加载算法」里有一步是把 `playbackRate` **重置成 `defaultPlaybackRate`**;而 `applyRateToEl` 的每个调用点都在设 `src` **之前**(切集时 `<video>` 按 `stream_url` 重建,得在新元素上先落倍速)→ 设完就被下一行的 `el.src = …` 抹掉。首播看不出来是因为 core 新点播本就把倍速复位成 1(§7.1 队列级粘住:新点播复位 / 切集沿用),**只有切集捎带非 1 的倍速过来才露馅**。
  - **定案手法 = 预览浏览器(Chromium,与 WebView2 同内核)四组对照**,别靠读规范猜:(A) 全新元素先设 1.75 再设 src → **重置成 1**;(B) 已加载过的元素换 src → **重置成 1**;(C) 全新元素 + `URL.createObjectURL(MediaSource)`(自适应 / shaka 都走这形)→ **重置成 1**;(D) 先设 `defaultPlaybackRate = 1.75` 再换 src → **保持 1.75**。注意 (A):规范把这步写在「networkState 不是 NETWORK_EMPTY」的分支里,按字面读全新元素不该被重置 —— **实测照样重置**,所以这条只能量不能推。
  - **修 = `applyRateToEl` 里连 `defaultPlaybackRate` 一起设**(一行)。它同时治好一个还没被撞见的隐患:shaka 5.1 的 `PlayRateController` 拿 `video.defaultPlaybackRate` 当「缓冲卡顿 / 退出 trick play 后恢复到多少」(`lib/player.js` 的 `getDefaultRate` 与 5320–5327 行)—— 不设它的话,B 站那条路上只要卡一次冲就把用户的倍速打回 1.0。
  - **判据留给后人**:凡是「设了某个媒体元素属性、随后又设 src」的写法都要问一句「加载算法会不会把它抹掉」;`volume` / `muted` / `loop` 不在重置清单里(所以那几处一直没事),`playbackRate` 在。

## 进度条上的片头片尾标记改成可拖(2026-09-10·二)

> 来源:2026-09-10 用户追加「片头片尾能不能支持下拖动就从该集生效,这样调整也方便;看看好不好支持」。规则句在 AGENT §7.1(片头片尾条)。

- **答案是「好支持」,而且 core 一行不用改** —— 这条值得记,因为它是「原语接口留对了」的一次兑现:`skipctl.rs::mark_skip(action, Some(secs))` 本来就收任意秒数、锚在当前集、**从这集起生效**、继承其它项、自己校验顺序、落库后重算并广播 `MediaEvent::Skip`;前端 `markSkip` 也早就是 `(action, secs?)` 的形。右键菜单传的是「光标处的秒数」,拖动传的是「拖到的秒数」—— **同一个入口,只是秒数从哪来不同**。用户问的「从该集生效」正好就是手标的既有语义,不用新增任何东西。
- **抓手与线分开**:线只有 2px(细才好看、才不遮画面),但 2px 的抓手抓不住 → 元素本身是 14×18 的透明块,线画在 `::before` 里;hover / 拖动时线加粗到 3×15 并点一层辉光(`cursor: ew-resize` 之外再给一个看得见的反馈)。
- **不留死区**:标记现在吃指针事件了,而进度条是「点哪跳哪」——三个 14px 的抓手若把点击吞掉,条上就多了三处「点了没反应」。解 = **按下没挪过 3px 就当普通点击**,松手时自己 `seek` 到那个位置。于是这三处的点击行为与条上别处**完全一致**,只有「从这里开始拖」才是新手势。
- **顺手修掉一处一直存在的错位**:标记原先用 `left: pct%` 定位(整条轨道),而 range 的拇指与 hover 读数用的是**可用轨道**(两端各让出半个拇指)—— 同一秒数两者能差 5px。平时看不出来,但**刚自动跳完片头时播放头正停在「片头止」标记上**,那点错位一眼就能看见;拖动之后更要紧:你放在光标处(可用轨道换算),它渲染到别处(整轨换算)。改成 `left: calc(5.5px + var(--p) * (100% - 11px))` 后预览量出来标记中心与拇指位置**同为 412.3px**,分毫不差。
- **两个「别把片子从用户手底下换掉」的守卫**(都是拖动带出来的新路径):① 拖标记期间整段 skip 判定跳过 —— 播放头照常往前走,越线切集会在拖到一半时换集,拖完的标记还落到了下一集;② **越线判据从「已经在线后面」(`p >= outro_start`)改成「这一拍跨过」(`prev < outro_start && p >= outro_start`)** —— 否则把片尾标记往回拖到播放头**之前**,下一次 timeupdate 就当场切集(用户只是想调标记)。第二条顺带也让「skip 信息迟到」这类情况不再回溯触发。
- **落库前的乐观位置**:松手到 core 广播回新 skip 之间若不占位,标记会先弹回旧位再跳到新位,看着像「白拖了」→ `pendingMark` 顶着,`watch(skipInfo)` 到了就清,2 秒兜底(core 拒了也不会永远卡在拖后的位置)。
- **邻居夹 1 秒**:core 那边「起点拖过终点就把起点丢掉、退回从 0 算」的兜底是对的**数据**语义,但作为**手感**很糟(标记突然消失)→ 前端夹成拖不过去(`MARK_MIN_GAP_S`)。两层不冲突:前端管拖不过去,core 管别的入口(嘴控 / 菜单)传进来的怪值。
- **发现性**:拖动是看不见的手势 → 右键菜单里加一行禁用项「条上的小竖线可以直接拖着调」(`media.skip.dragHint`),菜单本来就是发现这套功能的地方。
- 预览页验的七项:三个标记反算回来正好 5 / 90 / 290 秒 · 标记中心与同秒数的拇指位置重合 · 标记中心命中 `.skip-mark`、旁开 30px 仍命中 `.slider` · 拖片尾 290→240 跟手且落 OSD「已记下,从本集起生效」· 片头止拖过片尾夹到 289、片头起拖过片头止夹到 89 · 按下不动松手 = seek 到 290 且标记没动 · 把片尾拖到播放头后面不切集 / 正常播过去照切。

## 更正:标记条颜色改成跟皮肤走(2026-09-10·三)

> 来源:2026-09-10 用户「那个标记条看下 能不能和皮肤联动;不然有些突兀」。**更正上一节**(2026-09-10·二)里「颜色用 `--attn`(琥珀)不是 `--accent`」那条 —— 那条是错的,规则句以 AGENT §7.1 为准。

- **错在哪**:`--attn` 确实是语义 token、确实每套皮各有定义,所以「跟着皮肤走」在**字面上**成立 —— 但它的**角色是「警示」**,四套皮里它一律是琥珀/橙。把四套皮的两个值摆一起才看得出问题:

  | 皮肤 | `--accent`(轨道色) | `--attn`(标记色) | 结果 |
  |---|---|---|---|
  | scifi | `#5fd2ff` 亮青 | `#ffb86b` 琥珀 | 青橙互补,**硬撞** |
  | warm | `#e0904a` 暖橙 | `#e8884a` 暖橙 | 几乎同色 → 已播区**隐形** |
  | green | `#5a8f6a` 青苔绿 | `#c2814e` 棕橙 | 撞 |
  | night | `#c9a96a` 暖琥珀 | `#d99a5f` 暖橙 | 几乎同色 → 已播区**隐形** |

  也就是说它同时犯了两头:在冷色皮里跳，在暖色皮里消失。而我当初写下「与 accent 拉开对比」这句判断时,**只对着科幻皮眼验过** —— 唯一那套「拉开对比」碰巧成立、且成立得过头的皮。
- **教训(比这个 bug 本身值钱)**:① **「用了语义 token」≠「跟皮肤协调」** —— token 只保证「换皮会跟着变」,不保证「变出来的那组值彼此好看」;挑 token 要挑**角色**对的那个,不是挑「当时这套皮里看着顺眼」的那个。② 颜色类改动**必须四套皮各看一眼**(scifi / warm / green / night),科幻皮是深底冷色,和另外三套的明度与色相关系完全不同,单验它等于没验。
- **改法**:不换色相,换**明度** —— `color-mix(in srgb, var(--accent) 32%, #fff)`。同一个色相所以放进哪套皮都不跳;提亮一档所以压在纯 accent 填充的已播区上仍是一道看得见的刻痕(再加原有的 1px 黑描边补分界)。新皮肤零改动自动正确(比新开一个 `--mark` token 更守 §6.7 的「加皮肤 = 加 token 块,组件零改动」——后者还要皮肤作者记得多定义一个名字)。
- **老 WebView2 兜底**:`color-mix` 要 Chromium ≥111。不认它的 runtime 会把**整条 `background` 声明**丢掉 → 标记变透明 = 静默消失(§3.5)。所以前面留一行 `background: var(--accent)`:老引擎退成纯 accent,已播区上靠黑描边仍看得见,不至于没了。真机判据 = 标记若看着和轨道**完全同色**,说明那台机器的 WebView2 老于 111。
- 四套皮 1:1 截图逐一看过(播放头放在 2:30,让两个片头标记落在已播区、片尾标记落在未播区,一屏同时看两种底)。

## 起点贴着 0 就不画那根线(2026-09-10·四)

> 来源:2026-09-10 用户「片头开始那个时间有什么用」→ 摸清用途后给了两条路,用户选「起点贴着 0 时不画那根线」。规则句在 AGENT §7.1,常量进 §4.11 待确认。

- **先答那个问题:`intro_start` 在 core 是可选的**(`skip.rs:132` `r.intro_start.unwrap_or(0.0)` —— 必需的是 `intro_end`,那是跳过去的落点)。它只有两件活:
  ① **触发闸**(`VideoOverlay` 位置 watcher):只有播放头**自然走进** `[start, end)` 才跳。这在片头不在最开头时是刚需 —— 很多剧先来一段前情提要 / 冷开场,OP 到 2:30 才起;起点若当 0 算,一开播就会被从头甩到 4:00,把冷开场整个吞掉。
  ② **「回看」的落点**:跳过后那句「已跳过片头 · 回看」点了是回到 `intro_start`,不是回到 0。
- **所以「觉得它没用」是对的 —— 在片头就从头开始的片子上**(最常见)。那时 start≈0,两件活都退化,线钉在最左边、起播时还被播放头拇指压着。
- **改法**:`INTRO_START_MIN_S = 10`,起点在前 10 秒内就不画那根线。10 秒的理由 = 够盖住片方 logo 那几秒,又远小于任何真冷开场(前情提要总是几十秒起)。**功能一点没动** —— 触发闸与回看落点照常用那个值,只是不给手柄;真要设更小的起点仍走右键菜单「片头从这里开始」。
- **必须一起做的那半:同一个数也是它的拖动下限**。只加「不画」不加「夹住」的话,把起点往左拖过 10 秒 → 松手落库 → 下一帧那根线按新规则消失 = **手柄被自己拖没了,还拖不回来**(只能改走右键菜单)。所以 `clampMark('intro_start')` 的 `lo` 直接取 `INTRO_START_MIN_S`,拖到下限就停住。**这类「隐藏条件」与「可达性」成对出现的地方都要这么对一眼:把一个控件藏起来的规则,不能让用户自己操作出来。**
- 预览验的边界:start=5 / 9.9 → 只画 2 根;start=10 → 画 3 根;冷开场 150–200 → 画 3 根;从 150 一路往 0 拖(含拖出条外)→ 停在 10、松手后标记还在(count=3)。
